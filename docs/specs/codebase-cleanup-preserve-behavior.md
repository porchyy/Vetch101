# Spec: จัดระเบียบโค้ด Vetch101 โดยคงพฤติกรรมเดิม

## Problem Statement

ผู้ใช้ต้องการให้โปรเจ็กต์ Vetch101 อ่านง่าย หาไฟล์ที่เกี่ยวข้องกับงานหนึ่ง ๆ ได้ง่าย และแก้ไขต่อได้โดยไม่ต้องไล่ความสัมพันธ์กระจัดกระจาย ทั้งที่แอปปัจจุบันทำงานได้หลายอย่างแล้ว การรื้อโดยไม่มีขอบเขตอาจทำให้ Media Inspection, Media Pipeline, ประวัติ, การอัปเดต หรือการแพ็ก Windows เปลี่ยนพฤติกรรมโดยไม่ตั้งใจ

การตรวจทุกไฟล์ที่ทีมดูแลเองพบจุดที่ควรแก้จริง ได้แก่ การแพ็ก All-in-One Distribution ที่ยังไม่ยืนยันเครื่องมือใน `bin`, callback ที่อาจใช้ Browser Target เก่า, การแจ้งเตือนรูปซ้ำ, โค้ดหน้าจอที่รวมหลายหน้าที่, ค่าบิลด์เฉพาะเครื่อง และเอกสารที่ไม่ตรงกับโค้ดปัจจุบัน หลักฐานและข้อจำกัดของการตรวจอยู่ในรายงานวิจัยที่อ้างไว้ท้ายเอกสาร

## Solution

ตรวจไฟล์ที่คนดูแลเองทั้งหมด แล้วจัดระเบียบเฉพาะจุดที่มีหน้าที่ซ้ำ ขอบเขตไม่ชัด หรือมีข้อผิดพลาดที่ยืนยันจากโค้ด ให้แต่ละงาน เช่น การตรวจสื่อ การดาวน์โหลด การอัปเดต และการแสดงผล มีที่อยู่และทางเข้าที่เข้าใจง่าย รักษาความสามารถ ข้อมูลในเครื่อง และรูปแบบการแจกจ่ายเดิมให้ครบ ตรวจผลจากพฤติกรรมที่ผู้ใช้เห็นและไฟล์ที่แพ็กจริง

เป้าหมายคือโค้ดที่ดูแลง่ายขึ้น ไม่ใช่การบังคับเขียนทุกไฟล์ใหม่หรือเพิ่มชั้น abstraction เพื่อความสวยงาม จำนวนไฟล์อาจเพิ่มหรือลดตามหน้าที่จริง

## User Stories

1. As a ผู้ใช้ Vetch101, I want วางลิงก์และทำ Media Inspection ได้เหมือนเดิม, so that ฉันยังเริ่มดาวน์โหลดได้ตามขั้นตอนที่คุ้นเคย
2. As a ผู้ใช้ Vetch101, I want ดาวน์โหลดวิดีโอในคุณภาพที่เลือกได้เหมือนเดิม, so that การจัดโค้ดไม่ทำให้ตัวเลือกหายไป
3. As a ผู้ใช้ Vetch101, I want ดาวน์โหลดเสียง MP3 และ WAV ได้เหมือนเดิม, so that งานเสียงที่ใช้อยู่ไม่สะดุด
4. As a ผู้ใช้ Vetch101, I want เลือกรูปและรูปแบบภาพจาก Photo Album ได้เหมือนเดิม, so that ฉันบันทึกเฉพาะรูปที่ต้องการได้
5. As a ผู้ใช้ Vetch101, I want ใช้ Direct Stream Ingestion กับลิงก์ HLS และ DASH ได้เหมือนเดิม, so that ลิงก์สตรีมตรงยังใช้งานได้
6. As a ผู้ใช้ Vetch101, I want เปลี่ยน Browser Target ก่อนดาวน์โหลดแล้วแอปใช้ค่าล่าสุด, so that Browser Session Handoff ใช้บัญชีจากเบราว์เซอร์ที่เลือกจริง
7. As a ผู้ใช้ Vetch101, I want ใช้ Anti-Bot Fallback ได้เหมือนเดิม, so that ฉันลองใหม่ได้เมื่อเว็บไซต์ปฏิเสธการตรวจสื่อ
8. As a ผู้ใช้ Vetch101, I want เห็นความคืบหน้าและยกเลิกงานได้, so that ฉันควบคุมงานที่ใช้เวลานานได้
9. As a ผู้ใช้ Vetch101, I want เมื่อยกเลิกหรือปิดแอปแล้ว process ลูกถูกจัดการเหมือนเดิม, so that ไม่มีงานดาวน์โหลดค้างโดยไม่ตั้งใจ
10. As a ผู้ใช้ Vetch101, I want ได้ Download Outcome ที่ตรงกับไฟล์ที่บันทึกจริง, so that เปิดไฟล์หรือโฟลเดอร์ปลายทางได้
11. As a ผู้ใช้ Vetch101, I want ประวัติและการตั้งค่าที่เก็บในเครื่องยังอยู่หลังอัปเดต, so that ไม่ต้องตั้งค่าใหม่
12. As a ผู้ใช้ Vetch101, I want ธีมและ Mascot Companion ทำงานเหมือนเดิม, so that การจัดโค้ดไม่เปลี่ยนประสบการณ์ใช้แอป
13. As a ผู้ใช้ Vetch101, I want ได้รับ notification หลังดาวน์โหลดรูปสำเร็จเพียงครั้งเดียว, so that ไม่เห็นข้อความซ้ำ
14. As a ผู้ใช้ Vetch101, I want อัปเดตแอปและ engine dependencies ได้เหมือนเดิม, so that ใช้งานรุ่นใหม่ได้โดยไม่ต้องตั้งค่าเอง
15. As a ผู้ใช้ Vetch101, I want การอัปเดตยังถูกกั้นระหว่าง Media Inspection และงานดาวน์โหลด, so that งานที่กำลังทำไม่ถูกตัดกลางทาง
16. As a ผู้ใช้ Portable Distribution, I want ไฟล์ ZIP มีแอปและเครื่องมือที่จำเป็นครบ, so that แตกไฟล์แล้วใช้งานได้ตามเงื่อนไขที่ระบุ
17. As a ผู้ใช้ Installed Distribution, I want installer มี engine dependencies ครบ, so that ติดตั้งบนเครื่องสะอาดแล้วเริ่มใช้งานได้
18. As a นักพัฒนา, I want หา logic ของการดาวน์โหลดและการอัปเดตได้จากขอบเขตที่ชัดเจน, so that แก้เรื่องหนึ่งโดยไม่ต้องอ่านหน้าจอทั้งไฟล์
19. As a นักพัฒนา, I want ค่าคุณภาพสื่อที่แสดงและค่าที่ backend ยอมรับสอดคล้องกัน, so that เพิ่มหรือแก้ preset โดยไม่ตกหล่นอีกจุด
20. As a นักพัฒนา, I want รู้ว่าฟังก์ชันและ model ใดมีผู้ใช้จริง, so that ลบของที่ไม่ใช้ได้โดยไม่ตัดทางเข้าที่จำเป็น
21. As a นักพัฒนา, I want clone โปรเจ็กต์ไปอีกเครื่องแล้วบิลด์ได้โดยไม่พึ่งพาพาธส่วนตัว, so that ทำงานร่วมกันและปล่อยรุ่นได้
22. As a นักพัฒนา, I want คำสั่งเริ่มแอปและเอกสารตรงกับโค้ดและรุ่นที่เผยแพร่, so that ไม่เสียเวลาไล่คำสั่งหรือสถานะที่ล้าสมัย
23. As a นักพัฒนา, I want ผลทดสอบเดิมเป็น baseline และมี regression เฉพาะจุดที่เปลี่ยน, so that ตรวจได้ว่าการจัดโครงสร้างรักษาพฤติกรรมเดิม
24. As a ผู้ดูแล release, I want ตรวจเครื่องมือและไฟล์ภายใน artifact ที่สร้างจริง, so that การบิลด์ผ่านไม่ถูกเข้าใจผิดว่าแพ็กครบแล้ว

## Implementation Decisions

- **ยืนยันโดยผู้ใช้:** ตรวจทุกไฟล์ที่ทีมดูแลเองเพื่อหาจุดจัดระเบียบ และรักษาความสามารถเดิมทั้งหมด การตรวจครอบคลุม frontend, Rust backend, tests, scripts, configuration และเอกสาร ส่วน generated files, dependency trees และ binary artifacts ให้ตรวจในฐานะผลลัพธ์หรือแหล่งข้อมูล ไม่จัดรูปแบบเนื้อหาที่เครื่องมือสร้าง
- **ข้อเสนอด้านลำดับงาน:** ทำ baseline ของพฤติกรรมและ release artifacts ก่อน จากนั้นแก้ข้อผิดพลาดที่มีหลักฐานชัด จัดโครงสร้าง frontend/backend เฉพาะจุด เก็บ script/config/docs ที่ซ้ำหรือล้าสมัย และตรวจ packaged app ปิดท้าย แต่ละช่วงต้องยังบิลด์และทดสอบได้
- **ข้อเสนอด้านเทคโนโลยี:** คง Tauri, React, TypeScript และ Rust; เป้าหมายของงานนี้คือความเป็นระเบียบของโค้ด ไม่ใช่การเปลี่ยน UI framework การย้ายไป WinUI ยังไม่ใช่ข้อตกลงของผู้ใช้
- ให้ส่วนหน้าจอรับผิดชอบการแสดงผลและการผูก action เป็นหลัก ย้ายการประสานงานของ App Update และ Engine Dependency Update ที่มี state/effects ของตัวเองออกจากส่วนแสดงผลเมื่อทำให้ขอบเขตชัดขึ้น คง Download Session controller และ reducer ที่ใช้อยู่ ไม่แตกไฟล์เพราะจำนวนบรรทัดอย่างเดียว
- คง Media Inspection และ Media Pipeline เป็นทางเดินหลักของสื่อ รักษา tagged media model, Download Outcome, Concurrency Guard และการจัดการ process บน Windows ทบทวนบทบาทของ pipeline ที่ปัจจุบันตรวจปลายทาง ถือ lock และส่งต่อให้ตัวดาวน์โหลด; ชื่อและขอบเขตต้องตรงกับงานจริง
- ให้รายการ preset คุณภาพที่แสดงกับ allowlist ฝั่ง backend ใช้กฎเดียวกันโดยยังตรวจ input ที่ขอบเขต Rust อยู่ ห้ามลดการตรวจ URL, format หรือ path เพื่อให้โค้ดสั้นลง
- แก้การใช้ Browser Target เก่าระหว่าง Media Inspection กับการเริ่มดาวน์โหลด และให้การแจ้งเตือนเมื่อดาวน์โหลด Photo Album สำเร็จเกิดเพียงครั้งเดียว
- ให้กระบวนการ release ระบุและตรวจ engine dependencies ทั้งสามตัวก่อนแพ็ก ตรวจผลการสร้าง ZIP และตรวจ artifact จริงหลังบิลด์ ไม่ถือว่าการพบเครื่องมือบน PATH ของเครื่องพัฒนาเป็นหลักฐานว่า All-in-One Distribution ครบ
- เอาค่า build directory ที่ผูกกับเครื่องหนึ่งออกจาก config ที่แชร์กัน เก็บ implementation ของสคริปต์เริ่มแอปเพียงแห่งเดียว และทบทวน public wrappers, IPC commands, models หรือ comments ที่ไม่พบการใช้งานก่อนลบ
- ทำเอกสารรุ่นปัจจุบัน คำสั่งทดสอบ และสถานะ issue notes ให้ตรงกับข้อเท็จจริงที่ตรวจได้ แยกรุ่นของ source กับรุ่นที่เผยแพร่แล้ว และไม่แก้สถานะ issue แบบเหมารวม

## Testing Decisions

- ทดสอบพฤติกรรมที่สังเกตได้ ไม่ยึดจำนวนไฟล์ ชื่อ hook หรือโครงสร้างภายในเป็นเงื่อนไขผ่าน
- ใช้ seam เดิมที่สูงที่สุดเท่าที่เหมาะ: ทดสอบ Download Session จากการเปลี่ยน Browser Target จนถึง argument ที่ส่ง IPC; ทดสอบ media result และ history จาก outcome ที่คืนมา; ทดสอบ backend Media Pipeline/command boundary ด้วย fixture โดยไม่พึ่งเครือข่ายเมื่อทำได้
- สำหรับ release ให้ตรวจ artifact จริงของ Portable Distribution และ Installed Distribution ว่ามีแอปและ engine dependencies ครบ ตรวจเปิด/ปิดแอปบน Windows และทดสอบ installer บนเครื่องหรือ VM สะอาดเมื่อพร้อม การตรวจหน้าต่างอย่างเดียวไม่ยืนยันว่าดาวน์โหลดจากเว็บไซต์จริงได้
- ใช้ชุด Node tests, Rust unit tests, network integration test ที่มีอยู่ และสคริปต์ portable/native/installer smoke เป็น prior art; เพิ่ม regression เฉพาะข้อผิดพลาดหรือสัญญาที่การจัดโครงสร้างแตะ ไม่สร้าง test suite ซ้ำทั้งระบบ
- หลังแต่ละช่วงให้รันการตรวจที่เกี่ยวข้อง; ก่อนส่งมอบให้รัน frontend build/tests, Rust tests และ Windows package smoke ตามสภาพแวดล้อมที่มี พร้อมระบุสิ่งที่ยังตรวจไม่ได้อย่างตรงไปตรงมา
- จุดทดสอบที่เสนอนี้ยังรอผู้ใช้ยืนยันว่าตรงกับความคาดหวัง โดยเฉพาะการทดสอบ installer บนเครื่องสะอาดและการดาวน์โหลดจากเว็บไซต์จริง

## Out of Scope

- การเพิ่มฟีเจอร์ดาวน์โหลดใหม่ เว็บไซต์ใหม่ ระบบคิวหลายงาน หรือเปลี่ยนหน้าตาแอปครั้งใหญ่
- การย้ายจาก Tauri ไป WinUI 3 หรือเปลี่ยนภาษา/framework โดยไม่มีข้อตกลงใหม่
- การเขียนทุกไฟล์ใหม่เพียงเพื่อให้ต่างจากของเดิม หรือเพิ่ม dependency/abstraction ที่ยังไม่มีงานจริงรองรับ
- การสร้างเสียงบรรยาย WAV/MP3 ซึ่งเป็นร่างงานแยกจากฟีเจอร์ดาวน์โหลดเสียงปัจจุบัน
- การเผยแพร่ release ใหม่หรือเปลี่ยน artifact ที่ผู้ใช้ติดตั้งอยู่โดยอัตโนมัติ
